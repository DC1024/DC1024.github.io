方法与边界

这份画像不是心理测评，也不是社交标签。它只回答一个问题：从一个人实际做过的事、留下的记录、给出的反馈里，能稳定地看出什么。

材料有三类：跨项目长期记忆（工具铁律、服务器、发布链路、代码调研原则）、各工作区的日志（项目推进过程与踩坑复盘）、以及身份与偏好文件（称呼、城市、长期关注）。这些记录有一个天然偏向：它们几乎全部由「做事」产生，因此更能反映工作人格，而不是私人生活。凡是推断，我会写明「推断」；凡是有原话，我会尽量引原话。

READING记录里出现频率最高的词不是「喜欢」或「想要」，而是实测、复核、回验、判据、根因、硬门槛。语言习惯本身就是性格证据。
01

性格底色：五个稳定的切面

TRAIT 01 / EPISTEMIC

证据癖：不相信「应该好了」

DC 对世界的默认假设是「它会坏」，所以任何结论都必须带证据链。这不是谨慎，而是一种近乎道德要求的认知习惯：没有观测到的成功，不算成功。

2026-09-28回读 GitHub Release 正文时反复出现 U+FFFD 替换字符，看起来像中文被写坏。他没有直接重写，而是先做受控实验（短文本往返无损）、再抓渲染页 HTML 交叉验证，最终确认是本机 TLS 中间人读取链路损坏，服务端存储是好的。先怀疑自己，再怀疑链路，最后才怀疑对方。
2026-09-22同一批镜像源，探针说「传输被中断」、真实 docker pull 说「全部成功」。他没有二选一，而是要求两条结论都写进文档——因为它们测量的是不同路径。判断「慢」还必须带单位：102.6 KiB / 15 秒 = 7 kB/s，不是「稳定断在 102.6 KiB」。
2026-10-13只靠 grep "stuck" 看到失败码，就下过「该项目零脱困反射」的结论；精读后发现 MoveToSkill 自带三档脱困，方向完全相反。这次代价被写成了「代码调研铁律」：失败码的存在恰恰说明该路径被显式处理过，看到失败码要去读它的上游。

最能说明问题的是部署纪律：改完代码不算完，容器内 md5 必须等于本地 md5；「构建成功」和「线上真的换了」是两件事；「报失败」也可能已经删掉了——要 Test-Path 复核。他对「假绿」的容忍度，远低于对失败的容忍度。

TRAIT 02 / PERFECTIONISM

掌控型完美主义：差 1px 也不行，但必须发货

他的完美主义不是审美式的拖延，而是用工程纪律把标准钉死。GT7 仪表盘从首日 18 项测试起步，一路加到 226 → 231 → 277 → 321 → 406 项；九套主题（auto/light/dark + oled/sepia/racing/glacier/hud/midnight）用 data-theme 统一切换，并逐套校验对比度。WUD 汉化把语言包做到 502/502 中英严格对称，并用 CI 守卫防止回退。

但他不是「永远在打磨、从不发布」的人。AutoAudioSwitcher 发到 v1.1.3，WUD 发到 beta1.5，winprintdiag 发 v1.0.0，MirrorPilot 从 v0.1.0 一路发到 v0.3.1。他的完美主义有出口：先定验收判据，再允许发货。

2026-10-02为一个中文段落的排版，他要求检查「源码换行落在两个汉字之间」造成的半角豁口；全站 7 个多行 <p>，实际需要改 5 处，逐处给出判定依据。这种问题用「字数 × 字号」永远算不出来，只能渲染后实测。
TRAIT 03 / AUTONOMY

反中间商：不能接受「被别人卡住」

他对「依赖一个自己无法检查、无法替换、无法退出的东西」有近乎生理性的不适。所有机器都没有稳定海外网络，这个硬约束没有让他妥协，反而逼出了一整套「借别人的机器出海」的方案：华为云 SWR 公益中转、GitHub Actions 搬到阿里云 ACR、按需选择镜像源。他不接受「本机回源」这种听起来正确但根本跑不通的方案。

选型上他有一条清晰的红线：拒绝闭源中间件；非商业项目只接受绝对免费的来源。KSpeeder 被否掉的理由不是不好用，而是「用别人免费节点还卖钱」。此后给建议时，「付费 / 会员 / 闭源」三个词基本从选项里消失。

长期五台机器（Ubuntu、Arch、PVE、iStoreOS、Z4Pro）全部自持，三十多个容器自己编排；监控、更新、镜像、网盘、旅行规划、Docker 更新检测，能自建的绝不托管。这不是省钱，是把控制权留在自己手里。
TRAIT 04 / OWNERSHIP

所有权意识：这是我的作品，不是我的 fork

AutoAudioSwitcher 这件事很能说明他的边界感。代码归属实测约 70.8% 为新增，但架构骨架与音频管理核心思路源自上游 Apache 2.0 项目。他明确说过：我一开始不是说了要自己开发吗，不接受「fork / 二次开发」的对外表述；同时，上游署名必须保留，英文版措辞从「fork」改成「enhanced edition」。

这不是虚荣，而是一种「署名与归属必须准确」的原则：既不抹掉别人的贡献，也不把自己的劳动挂到别人名下。他会在意 README 的中文首页、Release 说明、站点文案的调性——因为那是作品的「门面」，也是作者对读者的交代。

TRAIT 05 / RHYTHM

夜行性长耐力：高峰在 23 点到凌晨 3 点

把 179 份按日期命名的日志的写入时间按小时统计，48.0% 落在 23:00–03:00；算上 22 点则达到 56.4%——超过一半。峰值在 00:00（29 次），深夜 0 点的记录比上午 9 点（5 次）多近六倍。工作区从 8 月 30 日到 10 月 18 日共 167 个，平均每天 3.3 个会话——这不是「偶尔熬夜」，而是一种稳定的夜间工作节律。

02

兴趣地图：玩，也要玩到拆开看

他的兴趣有一个共同结构：先作为用户享受，再作为工程师拆解，最后做成自己的工具。很少停在「消费」这一层。

2.1游戏：不是消遣，是研究对象

GT7 是最典型的例子。他不满足于看游戏里的仪表，而是自己写遥测记录器，解析 296 字节的 UDP 广播包，把 52 个字段里真正有用的 8 个挖出来做分析；随后又发现 wheel_rads 可以自标定轮胎半径、算滑移率与抱死，做出分段计时、理论最快圈、进站窗口、名次时间线。再接一个语音教练，实时播报「轮胎太凉，轻拖刹车升温再推」。

记录他会为一个「潜在空间 +0.71%」反复核对：不过滤异常圈会得到 +8.48% 的假空间，过滤后才是真实值；前后轴半径必须分开标定（0.3391 vs 0.3435 m），合并会引入约 1.3% 偏差。这已经不是在玩游戏，是在做赛车工程。

Minecraft 也一样：不是为了建房，而是做 MinePilot 无头 AI 玩家——服务端内的 headless ServerPlayer、记忆库、权限模型、皮肤、RCON、自建配置面板。Steam 侧则是 ASF 多账号挂卡、S302、反代，把「玩游戏」变成一套可运维的基础设施。

2.2自建基础设施：把云依赖一个个拆掉

五台机器、三十多个容器、监控、自动更新、镜像源、网盘、Docker 更新检测、旅行规划器。每晚 20:00 自动批量更新，还带 dry-run 风险判定：apt 要检查待删包是否包含当前内核，Arch 要检查孤儿包有没有反向依赖，iStoreOS 没有 autoremove 就跳过。这套东西已经稳定跑了近两个月，记录里全是「第 N 次执行（成功）」「耗时 48 秒」「剩余 0 可升级」。

2.3视觉与排版：一条藏得很深的审美线

他做过梵高《向日葵》与《星月夜》融合的系列海报：奶油米、深棕、赭黄三色，衬线排版，后来又把文字换成 DM Serif Display + Instrument Serif 的英文艺术字体。Dashboard 侧则要求九套主题、强调色、密度、读数缩放，连「四张卡片必须并列一排，不能有一张被挤下去」都要管。

审美他对排版的容忍度是像素级的：中文源码换行产生的半角空格、1px 的对齐偏差、标签把一行撑成三行导致输入框错位——这些都会被指出来。但他的审美不是装饰性的，而是信息密度与秩序感：干净、对齐、可读、不喧哗。

2.4物理与数学：浪漫的硬核表达

连续两天做了两版黑洞渲染器：先是 blackhole-sim.html，第二天是 Schwarzschild-Eye.html。不是调用 three.js 贴图，而是手写 WebGL2、逐像素积分零测地线，用 RK4 自适应步长，做 Novikov-Thorne 薄盘温度剖面、多普勒频移 g⁴、普朗克谱 × CIE 1931 色度 LUT。临界冲击参数与解析解的误差做到 1.9e-7%，还内置「理论阴影环」叠加当回归测试。

这类项目没有任何商业用途。它存在的理由就是「把它算对，并且好看」。这是他身上最接近浪漫的部分——只不过浪漫的表达方式是偏微分方程。

2.5信息与消费：收集癖 + 参数党

每天拉 AI 日报，做成固定五版块（模型 / 产品 / 行业 / 论文 / 技巧）、全局连续编号、单文件零依赖的晨报仪表盘。收集银行信用卡是纯收藏，不为额度；挑二手 Windows 平板会把预算、尺寸、内存、硬盘、用途（浏览器 / WPS / 远程 / SSH）一条条列清楚，再逐轮收敛。

推断他喜欢的不是「拥有」，而是把一个领域摸清楚的过程：参数、边界、代价、替代方案。收集只是研究完成后的物证。
03

工作与学习：先建验证台，再写功能

如果只看一件事来判断他的工作方式，那就是：他花在「证明它对」上的时间，往往不少于「让它对」的时间。

3.1一个稳定的六步闭环

01
先读现场
源码、日志、二进制字符串、真实配置，不靠猜
02
做探针
小脚本验证可行性，先拿数据再动手
03
写实现
单文件 / 零依赖 / 向后兼容优先
04
建验证台
pytest、Playwright、像素断言、多视口
05
部署硬校验
md5 对齐、冒烟、线上探针
06
写回记忆
把坑固化成规则，下次不再踩

这套闭环在不同项目里反复出现：GT7 用 pytest 277 项 + 24 端点逐字节比对；WUD 用 425 个单测 + 14 视口 + 落地页 E2E；answer-sheet-builder 用 离线 11 个后端测试 + 43 项 UI 验证；MirrorPilot 用 多架构 CI + i18n 键对齐。他不是「先写完再想怎么测」，而是测试与实现同时长出来。

3.2学习方式：需求驱动 + 对照实验

他很少做「系统性学习」，而是遇到什么问题就钻什么问题，直到能自己复现。Arch 熄屏问题从 GNOME 的 gsd-power 追到内核 consoleblank 参数，再到 uinput 注入真实输入验证唤醒；Windows 更新收不到大版本，从「组织的策略」这句话追到第三方优化工具 Winhance 写下的注册表预设，再追到 ChangeHistory.txt 的铁证。每一步都不是查文档抄答案，而是设计一个能区分两种解释的实验。

他还有一个很罕见的习惯：跨项目对标前，先确认同一个概念在两边叫什么。numen 的 UnstuckChain 与 minepilot 的 stuckRecoveries + transientBlocked 命名完全不同，按对方的名字检索必然搜不到，从而得出「没有」的假结论。这条被写进了「代码调研铁律」。

3.3记忆外脑：把教训写成可执行规则

跨项目长期记忆 592 行，几乎每一行都是「症状 → 根因 → 判据 → 正确做法」的结构。比如：

场景被固化的规则
git 提交提交信息里不能出现反引号 / $()；多行一律用引号定界的 heredoc因为一次真实的 pathspec 报错，差点产生错误提交
Windows 脚本.bat 里一律不写中文，纯 ASCIIcmd.exe 按 OEM 代码页读批处理，中文会让解析直接崩
PowerShell参数模式下 + 不是数组拼接，必须 @($a) + @($b)曾静默丢字段、得出完全错误的结论
跨工具传文件不用 /tmp，一律用工作区内相对路径Git Bash 与 Windows Python 的 /tmp 不是同一个目录
部署「构建成功」≠「线上换了」；先按 head_sha 找 run，再取该 run 的 artifactartifact 列表顺序不可靠，id 大不代表新

这不是「记性好」，而是把一次性的痛苦转化为系统性的免疫力。他的记忆不是日记，是一份不断打补丁的操作系统。

3.4代码品味：在约束里做减法

MirrorPilot 用 Go 单二进制 + SQLite 纯 Go 驱动，避开 CGO，才能交叉编译和精简镜像；基础镜像选 alpine 而不是 distroless，因为 gcr.io 在那个网络环境里拉不到；Schwarzschild-Eye 是单文件 55KB、零依赖 WebGL2；MinePilot 面板是零依赖 Node，只用内置模块；答题卡制卡端是纯静态站点。他的技术选型第一原则不是「先进」，而是「在这五台机器的网络里真的能跑」。

偏好能少一个依赖就少一个；能一个文件解决就不拆三个；但该拆包时（MirrorPilot 的 web / auth / secret / store）会严格保持单向依赖，让安全关键包可以被独立审阅。减法在部署面，纪律在架构面。
04

价值排序：他把什么放在前面

价值观不是他说了什么，而是他在有代价的时候选了什么。下面每一条都对应一次真实的取舍。

排序他坚持的他因此放弃的
自主可控自建镜像面板、自建更新检测、自建监控、自建旅行规划器更省事的托管服务、更漂亮的商业面板、更快的上手速度
诚实删掉「免费模型」承诺、模型名不做预设、站点不贬损上游更好看的营销文案、更高的转化率、更「完整」的功能列表
可验证双证据链、md5 硬门槛、部署后冒烟、线上探针更快的交付节奏、更少的心力消耗
署名准确保留 Apache 署名，但坚持「原创增强」而非「fork」更简单的项目叙事、更容易的「站在巨人肩膀上」说法
隐私密码只进本地记忆；云端文档只留地址/端口/用户名；key 走环境变量跨设备便利、团队共享的顺手
公平拒绝「拿免费公共节点包装成收费服务」的工具一个可能很好用的闭源加速方案
长期Public 仓库换不限分钟 CI；ACR 个人版只做非生产用途短期更省事的私有仓库、付费额度
底线他对「被收割」极其敏感：免费额度、开源协议、上游署名、公共节点商业化，这些事在他这里不是「细节」，而是判断一个项目/一个人是否值得合作的前置条件。
05

交往风格：低冗余，高信噪比

他说话像在提交 issue：现象、期望、约束，三句话以内。没有寒暄，没有铺垫，也很少解释「为什么」——因为他默认你会自己去查。

5.1语言极简，动作明确

做3继续开始做保留不动还是不息屏好的合并把提交进仓库整洁一点点了没反应为什么没下完就校验

这些是记录里留下的原话（含口语与笔误）。他不在乎句子是否完整，只在乎信息是否足够让对方行动。反过来，他也要求对方不要用长篇解释浪费他的时间——「少前言、先动手、有判断」是他对协作方的基本期待。

5.2反馈方式：截图 + 逐条 + 复审

他很少给抽象评价，通常直接上截图或现象：「四容器卡片应该并列一排，现在有一张卡片被挤下去了，整个排版都变了」「手机上分页滑动没有了」「连'暂无正在下载的种子'提示都没有了」。GT7 那次，他逐条复审了 10 条反馈，其中 3 条要求本轮修，4 条指出「已有答案 / 你上次已修」，剩下的是「上轮已完成」。他记得自己提过什么，也会检查你是否真的改了。

原话就是我跟你提过的 bug——这句话出现的场景，通常是他已经给过一次机会，而问题又回来了。他的耐心是按「是否在推进」计算的，不是按次数。

5.3边界感：授权说得很清楚

他会明确划定操作边界：「只做判断、不做修改」「这个方案先保留，不做」「保留不动」。一旦规则建立，他又会给足授权：服务器批量更新只要无风险就直接执行，不要反复询问。这是一种「先立法、后放权」的协作模式：边界内你自己跑，边界外必须先问。

5.4冲突风格：直接，但对事

他否定一个方案时通常不绕弯：「这个不行，因为 X」。但他很少做人身评价，也不情绪化地重复抱怨；更多是把问题变成一个更精确的约束，然后让你重做。他也会主动给选择题（A/B/C），然后回一个「做3」——决策成本低，但要求选项本身是经过思考的。

5.5信任模型：可撤销的授权

他愿意把 root、PAT、服务器密码交给 AI，但这不等于无条件信任。他的信任结构是：先给小任务 → 看你是否能自己发现错误 → 再逐步放开权限 → 一旦发现「假绿」，信任回退。所以他会要求「拿不准就问一句」，也会在事后复盘中写下「推三小时的结论不如问一句」。

06

张力与代价：画像的另一面

一个人的强项和代价通常是同一件事的两面。下面这些不是缺点清单，而是他这套性格在现实里必然产生的摩擦。

完美主义 vs 收尾。记录里频繁出现「已推送，未部署」「已部署，但容器落后一个修订」「下次部署再补」。他能把一件事的测试从 18 项推到 406 项，但也容易在「最后一公里」留下尾巴——因为下一件有趣的事已经开始。
掌控 vs 放权。他希望 AI 能自己判断、自己动手，但又忍不住复核每一个细节。结果是他仍然在深夜亲自做最后验收。他想要的不是「少做事」，而是「事情按他的标准做成」。
怀疑 vs 依赖。他把 root 交给 AI，同时要求每条结论都有证据。这种关系更像「带一个很强的实习生」：授权很大，审计也很严。好处是质量高，代价是双方都累。
广度 vs 深度。50 天 167 个工作区、十几个仓库、五台服务器、游戏、设计、物理、硬件采购同时推进。兴趣驱动让他学得极快，但也意味着注意力被不断切分；有些项目停在「能跑」而不是「打磨完」。
夜行的复利与代价。深夜无人打扰，适合长链路排障；但 56.4% 的记录发生在 22 点之后，长期看是健康与判断力的隐性成本。他的产出曲线很漂亮，代价曲线不在记录里。
直率的效率与温度。低冗余的表达让协作极快，但在需要安抚、解释、共情的场景里，他可能显得冷。好消息是：他对「事情」很苛刻，对「人」并不刻薄——很少看到人身评价，更多是「这个不对，重做」。
07

整体总结

IN ONE PARAGRAPH

DC 是一个把「可验证」当作道德底线、把「自主可控」当作生活方式的独立工程师与创作者。他像运维一样思考世界：先假设会坏，再设计证据；也像设计师一样要求世界：差 1px 也不行。他的兴趣从来不止于消费——玩游戏要拆到 UDP 包和轮胎滑移率，看黑洞要手写零测地线积分，做汉化要把 502 条文案做到中英严格对称。他说话极简，反馈极具体，信任给得谨慎、撤得果断；他不接受闭源中间商、不接受「免费节点卖钱」、不接受用营销话术掩盖能力的边界。

他的强项是把复杂系统变成可交付、可复现、可维护的东西；他的代价是很难对自己满意，也很难把控制权真正交出去。理性是他最外层的壳，浪漫藏在两个地方：深夜的黑洞渲染器，和一张梵高配色的海报。

一个用「证据」对抗不确定性、用「自建」对抗被卡住、用「极简语言」驱动复杂系统的人。

附：与他协作的说明书

如果这份画像只用来做一件事，那就是让下一次协作少走弯路。

DO / 这样做

  • 先给结论，再给证据；能给表格就不给长段落。
  • 不确定就问一句，但别问已经决定过的事。
  • 说清楚「验收判据」，再动手。
  • 交付时附上可复核的产物：md5、测试数、命令输出、截图。
  • 发现方向错了，直接说「这个结论反了，因为 X」。
  • 把踩过的坑写进记忆，而不是只修当前这一处。

DON'T / 别这样

  • 别用「应该可以 / 理论上没问题」结案。
  • 别推荐闭源、付费、会员制的中间件。
  • 别把「构建成功」当成「已经上线」。
  • 别在没读源码前断言「这个功能不存在」。
  • 别反复询问已经授权过的安全操作。
  • 别用寒暄和铺垫稀释信息。
